# 九、SEO 技术设置

## 1. Canonical 与重复 URL

所有正式内容页使用 self-referencing canonical。

同义 URL、大小写 URL、尾斜杠版本和旧路径统一 301，不保留两套可索引页面。Google 会从相似或重复页面中选择代表 URL，因此最好主动统一 canonical，并只把 canonical URL 放入 sitemap。([Google for Developers][2])

筛选参数示例：

```text
/spells/?class=mage
/drops/?rarity=legendary
/dungeons/?stage=endgame
```

默认处理：

```text
canonical → 对应主 Hub
noindex, follow
```

只有某个筛选组合出现独立、稳定搜索需求，并且页面有独立正文时，才升级为可索引静态页。

---

## 2. Noindex 页面

以下页面不进入索引：

```text
站内搜索结果
空筛选结果
无限组合筛选
排序参数
用户收藏页
预览页
草稿页
无内容标签页
```

使用 `noindex` 时页面应允许爬虫访问，否则爬虫看不到该指令；不要把同一 URL 同时用 robots.txt 完全屏蔽。([Google for Developers][3])

---

## 3. Sitemap

建议生成：

```text
/sitemap.xml
/sitemap-pages.xml
/sitemap-dungeons.xml
/sitemap-spells.xml
/sitemap-items.xml
/sitemap-updates.xml
```

只放：

* 200 状态；
* canonical；
* 可索引；
* 有实际内容；
* 已发布页面。

Sitemap 可以帮助新站和少外链站发现 URL，但提交 Sitemap 不等于保证收录，因此核心页仍然必须能从首页和 Hub 页通过普通链接访问。([Google for Developers][4])

---

## 4. Schema

建议使用 JSON-LD：

| 页面                          | Schema                                       |
| --------------------------- | -------------------------------------------- |
| 首页                          | `WebSite`、`Organization`                     |
| Dungeons、Spells、Drops 等 Hub | `CollectionPage`、`ItemList`、`BreadcrumbList` |
| 攻略页                         | `Article`、`BreadcrumbList`                   |
| 实体详情页                       | `Article`、`BreadcrumbList`                   |
| 更新页                         | `Article`、`BreadcrumbList`                   |
| 有真实可见 FAQ 的页面               | `FAQPage`                                    |

不要为了“多 Schema”给游戏装备页添加虚假的 `Product`、价格、库存、评价或 Offer。结构化数据必须与页面真实可见内容一致，也不能标记隐藏或误导性内容。([Google for Developers][5])

---

## 5. 页面级 SEO 规则

每个页面统一执行：

```text
一个清晰 H1
Title 与 H1 语义一致但不完全机械重复
主关键词自然出现在首段
长页提供目录
图片文件名包含实体名称
图片有描述性 alt
显示首次发布与最后核验日期
显示当前适用版本
正文中链接到来源和相关实体
```

日期字段分开：

```text
datePublished
dateModified
lastVerified
verifiedForVersion
```

`dateModified` 不能因为构建部署自动变化，只有正文或数据真正改变时才更新。

# 十、数据可信度标准

全站数据统一分为四级：

| 状态                       | 含义                         |
| ------------------------ | -------------------------- |
| **Official**             | Roblox 页面、开发者公告或官方更新明确确认   |
| **In-game Verified**     | 当前版本游戏内截图或录屏验证             |
| **Community Confirmed**  | 多个独立玩家样本或视频能够交叉确认          |
| **Legacy / Unconfirmed** | 来自原版或单一社区说法，尚未确认适用于 Reborn |

每条关键数据至少保存：

```text
value
sourceType
sourceURL
evidenceNote
verifiedForVersion
lastVerified
confidence
```

特别需要隔离的数据：

* 原版 Dungeon Quest 与 Reborn；
* 旧版本与当前版本；
* 官方掉率与玩家观察掉率；
* 报价与真实成交；
* 游戏内金币购买与 Robux 购买；
* 官方 Discord 与社区 Discord。

```text

```

同时上线：

* 4–6 个高需求技能详情页；
* 4–6 个高需求武器详情页；
* 其他地牢先保留在 Dungeons Hub，资料够了再拆页。

第一周最终规模：

```text
15 个 Hub / Guide 页面
8–12 个实体页面
合计 23–27 个可索引页面
```

这与文件提出的 20–30 页成站规模接近，但避免一次生成大量相似模板页。文件原方案同样建议先上核心页，再按地牢和数据长尾扩展。

## 第 8–21 天：按 GSC 决定扩展

优先处理：

1. 有曝光、平均排名 8–30 的页面；
2. 已出现但当前页面回答不足的新查询；
3. 某个技能、地牢、装备开始获得独立实体词曝光；
4. 游戏更新新增的地牢、技能和交易机制。

判断规则：

```text
同一意图 → 加深现有页
明显不同意图 → 新建独立页
只有同义表达 → 不新建页
无数据、无搜索、无更新价值 → 暂不扩展
```

文件建议在新站前期优先用 `differences、gamepass、spells、trading` 破局，再通过版本更新和 GSC 数据扩展，这一执行顺序应保留。

# 十二、最终给 Codex 的项目范围

第一版不要实现社区、账号系统、交易市场或复杂计算器。最终 MVP 范围应锁定为：

```text
15 个核心页面

4 个结构化数据集合：
- dungeons
- spells
- items
- updates

完整 TDH
统一 canonical
可控 sitemap
版本与核验字段
三层内链结构
原版与 Reborn 数据隔离
无假 Codes
无假 Trello
无脚本或外挂教程
```

最终核心策略可以概括为：

> **首页拿 Wiki 泛词，Differences、Gamepasses、Spells、Trading 负责新站破局，Dungeons、Drops 和实体详情页负责形成长尾矩阵，Codes、Trello、Discord 只做可信状态入口，所有页面以当前版本、真实截图和可追溯数据作为反超普通 AI Wiki 的核心壁垒。**
